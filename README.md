# 拾流

仓库：https://github.com/zaiwuli/shiliu

无账号的资源采集与同步后台，支持文章管理、CSV 导入、智能增量或指定页采集、转换同步和中文日志。仅部署于可信网络。

## Docker 部署

镜像：`ghcr.io/zaiwuli/shiliu:latest`，GitHub Actions 构建 linux/amd64 与 linux/arm64。

复制 `.env.example` 为 `.env`，将 DATABASE_URL 指向已经初始化的 Avdb PostgreSQL 数据库，然后执行：

```sh
docker compose pull
docker compose up -d
```

打开 `http://主机:8000`。首次拉取 GHCR 镜像如果需要认证，请在 GitHub Packages 将包设为公开，或使用有 read:packages 权限的凭据登录 ghcr.io。

## 数据库

启动先检查 Avdb 原有 `article` 表及所需字段；缺少时启动失败，不自行创建或迁移 Avdb 主表。只自动创建以下 6 张采集器表：

- shiliu_article：采集与 CSV 导入的原始记录
- shiliu_article_converted：转换结果、内容指纹及同步状态
- shiliu_task：采集计划
- shiliu_batch：批次汇总
- shiliu_task_log：采集日志
- shiliu_config：网络及同步设置

不会创建额外的测试目标表或批次明细表。已有 shiliu_ 表直接复用，不自动改名、迁移或删除 sehuatang_collector_ 表，以免操作其他工具的数据。如上一版本已经在该前缀下存有采集数据，需要确认归属后再单独迁移。不要将开发测试库直接当作正式 Avdb 使用。

## 采集和同步

不填结束页时，连续指定页数没有成功新增文章才停止，默认 3 页，最多扫描 100 页；填写结束页则按范围抓取。两种方式均按 website + tid 跳过已有帖子，已进入补抓队列的帖子交给补抓处理。CSV 导入记录同样参与去重。

实时同步由爬取新增入库触发，无新增不触发；定时同步按 Cron 执行。独立兜底补同步只处理待同步记录，不限日期，失败和冲突由用户处理。所有触发共用同步锁，成功且内容未变化的记录跳过。CSV 导入可手动处理，定时或兜底也会处理。

magnet 与 edk 数组去重后换行写入 Avdb magnet，图片以逗号连接；已有同 tid 同站点仅标记存在，不覆盖。不同站点 ID 冲突保留待处理。

文章管理支持多选板块清理原始和关联转换记录，不删除 Avdb 主表。删除历史记录会改变智能爬取的停止依据。

## 本地构建

前端 `cd frontend && pnpm install && pnpm build`。后端安装 backend/requirements.txt，通过环境变量提供 DATABASE_URL，运行 `cd backend && python -m uvicorn app.api:app --host 127.0.0.1 --port 8000`。

镜像构建：`docker build -f backend/Dockerfile -t collector .`。推送 main、v 开头标签或手动运行 Actions 均会构建镜像。测试、运行数据、CSV 原始文件和本地密钥配置不提交。

## 失败与冲突处理

文章管理可按同步状态筛选，勾选记录或选择筛选全部后批量处理。
大小超出目标范围的失败项可预览确认“大小留空并同步”；仅转换结果和目标 size 写为 NULL，原始大小保留。正常 size 继续按 MB 原值传递。
冲突项由用户确认使用备用 TID（原始 TID × 10001），预览双方信息及占用情况；已占用的不会覆盖。自动同步不主动改号。
转换表增加 target_tid 和 size_cleared 字段，启动自动补充，无新增表。成功映射持久保存，后续同步复用。

实时同步遇到其他同步占用时在后台等待，不丢弃新增批次。正常采集结束后等待队列并补处理本批次待同步文章，页面显示采集与同步阶段；失败和冲突仍需手动确认。定时模式不触发实时收尾。运行日志最新记录显示在最上方。

## 从旧版升级

先停止旧版采集器，再将镜像地址改为 ghcr.io/zaiwuli/shiliu:latest 后启动。新版启动会在事务中将六张 immortal_ 表改名为 shiliu_，保留文章、设置、日志和映射；新旧同名用途表同时存在时停止迁移。Avdb article 不改名。旧版容器不要与新版同时运行；回退旧版需先反向迁移表名。
同步历史保存到原有批次及日志表，日志中的同步记录展示最近 100 次执行结果。历史版本未保存的同步执行无法补回。

## 自动失败补抓与断线恢复

原有板块结束补抓后仍失败的帖子进入 shiliu_retry（第七张采集器表）。无需创建计划，后台每分钟检查到期项，等待普通采集空闲后串行执行。额外自动补抓最多三次：首次等待5分钟，两次失败后分别等待30分钟、2小时；第三次失败转为待手动补抓。手动次数独立记录，手动失败不重置自动次数。
采集任务 → 失败补抓支持筛选、多选、筛选全选、手动补抓、重新开启自动补抓、忽略与删除。正在执行项不能修改；忽略持续屏蔽正常采集与自动补抓，删除只移除队列记录，未来抓取失败可能重新加入。
页面解析结果在入库前写入 /data/recovery，断线事务使用新连接按2、5、15秒重试；耗尽后停止推进并保留文件。后台恢复及下次采集开始前重放，按站点和TID去重。数据库异常不消耗网站补抓次数。请保留 /data 挂载及 recovery 文件。种子解析算法不变。
旧版批次中的历史失败列表不会自动导入补抓队列；新版运行后产生的失败开始自动登记。补抓原因目前记录“详情或附件未获得可用资源”，不推断无权限或资源永久失效。

## 正式任务台账

日志页提供采集台账、同步台账，按任务分页，支持每页 5 / 10 / 20 条和定时、手动、导入筛选。每行通过“展开 / 收起”查看板块明细、补抓记录及任务日志或同步历史，页面每 5 秒刷新。

采集新增按已提交入库结果计数，包含任务内补抓；后续额外补抓按原任务归属单独累计。新任务保存触发方式、名称、板块页数和结束原因；启动仅补充 shiliu_batch.details、shiliu_article.origin_batch_id 及采集器索引，不增加业务表、不修改 Avdb article。历史任务根据现存文章及原始结果还原，无法确定的信息标记“未记录”。

同步台账按文章当前状态去重统计，后续补抓同步归回原采集任务；删除暂存文章会影响当前同步数量。执行历史另有入口，保留最近 100 次记录，实时同步仍在固定 5 分钟时段结束后显示汇总。单次执行可能涉及多个任务，其汇总不会当作单个任务的文章数量。

自动补抓按原采集任务归批，等待同一批待处理项全部到期后执行；每轮只汇报一次结果。历史没有来源任务的补抓记录保留原队列，不猜测归属。
